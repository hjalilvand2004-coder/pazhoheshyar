# پژوهشیار۳۶۰ (PazhoheshYar360)

سامانه وب فارسی، راست‌چین و واکنش‌گرا برای **کشف استعداد پژوهشی، اتصال دانشجو و استاد، تشکیل تیم پژوهشی و مدیریت مسیر پژوهش تا انتشار** — عضو اکوسیستم دانشجو۳۶۰.

- **بک‌اند:** FastAPI (پایتون) با معماری سرویس‌محور — هر بخش، API مستند و مستقل برای استفاده سایر سامانه‌ها
- **فرانت:** React (Vite) فارسی راست‌چین با فونت آفلاین وزیرمتن
- **ورود:** فرم لاگین محلی + **ورود یکپارچه با پرتال دانشجویار۳۶۰ (OIDC، Authorization Code + PKCE/S256)** با اعتبارسنجی کامل id_token (RS256) و اتصال هویت از طریق `issuer + sub`
- **نسخه قابل اجرا بدون پایتون:** بسته PyInstaller (تک‌فایل اجرایی) و Docker

---

## ۱) اجرای سریع

### راه الف — بدون نیاز به پایتون/پای‌چارم (سیستم مقصد)

**با فایل اجرایی:**
روی یک سیستم ساخت (ویندوز یا لینوکس با پایتون)، یک‌بار بسته بسازید و خروجی را به هر سیستم دیگری منتقل کنید:

```bat
REM ویندوز — دابل‌کلیک یا از cmd:
scripts\build_portable.bat
REM خروجی:
REM   dist\Pazhoheshyar360-Windows\           ← پوشه قابل انتقال (exe + START-WINDOWS.bat + راهنما)
REM   dist\Pazhoheshyar360-Windows.zip        ← همان بسته، آماده ارسال
```

فرانت‌اند ساخته‌شده داخل مخزن (`frontend/dist`) نگه داشته می‌شود؛ بنابراین برای ساخت بسته ویندوزی به Node.js هم نیازی نیست (اگر Node نصب باشد، فرانت دوباره ساخته می‌شود).

```bash
# لینوکس/مک (معادل همان کار)
bash scripts/build_portable.sh
# خروجی: backend/dist/pazhoheshyar360-server
```

توجه: PyInstaller چندسکویی نیست؛ بسته ویندوزی باید حتماً روی ویندوز با `scripts\build_portable.bat` ساخته شود.

**ساخت خودکار بسته ویندوزی با گیت‌هاب اکشنز (بدون نیاز به سیستم ویندوزی):**
کافی است یک تگ نسخه پوش کنید؛ workflow «Release» روی رانر واقعی ویندوزِ گیت‌هاب بسته را می‌سازد،
تست دود (اجرای واقعی exe و پاسخ سرور) می‌گیرد و zip را در بخش **Releases** همین مخزن منتشر می‌کند:

```bash
git tag v1.0.0
git push origin v1.0.0
# سپس: صفحه Releases مخزن ← فایل Pazhoheshyar360-Windows-v1.0.0.zip
```

(اجرای دستی هم ممکن است: تب Actions ← «Release — ساخت بسته پرتیبل ویندوز» ← Run workflow)

سپس روی سیستم مقصد (بدون پایتون): فایل را اجرا کنید و در مرورگر `http://localhost:8000` را باز کنید.
داده‌ها کنار فایل اجرایی در پوشه `data/` و فایل‌ها در `uploads/` ذخیره می‌شوند.

**با Docker (بدون پایتون، سرور/دسکتاپ):**

```bash
docker compose up --build
# مرورگر: http://localhost:8000
```

## ۲) معماری سرویس‌محور (قابلیت ارائه سرویس به سامانه‌های دیگر)

همه سرویس‌ها زیر `/api/v1/` و مستند در **Swagger: `/docs`** هستند. فهرست کامل قابلیت‌ها: `GET /api/v1/services`.
احراز هویت سرویس‌به‌سرویس با هدر `X-Service-Token` (متغیر محیطی `SERVICE_TOKEN`)؛ جریان رخدادها برای اعلان/تحلیل سایر سامانه‌ها: `GET /api/v1/events`.

| ماژول | شرح |
|---|---|
| `auth` | ورود محلی + SSO/OIDC، اتصال هویت مرکزی (issuer+sub) |
| `profiles` | پروفایل پژوهشی دانشجو/استاد با تفکیک فیلدهای حساس |
| `topics` | بانک موضوعات و الگوهای استاندارد استاد |
| `requests` | ثبت درخواست، استخر پژوهشی، ماشین وضعیت، محرمانگی، تأیید دانشگاه |
| `offers` | اعلام آمادگی، پذیرش/رد با قفل اتمی ضد تعارض |
| `conversations` | گفت‌وگو: پیام، فایل، جلسه، گزارش سوءاستفاده |
| `agreements` | توافق‌نامه همکاری و امضای دوطرفه |
| `projects` | اعضا، وظایف، جلسات، فایل‌ها، پیشرفت، خاتمه |
| `files` | بارگذاری/دانلود امن با نام غیرقابل حدس و کنترل دسترسی |
| `notifications` | اعلان‌های درون‌سامانه‌ای |
| `events` | جریان رخدادها برای اکوسیستم |
| `ai` | تطبیق، پیشنهاد موضوع، تحلیل استعداد، پایش پیشرفت، مجله/گرنت (قاعده‌محور و برچسب «آزمایشی») |
| `admin` | شاخص‌ها، کاربران، تنظیمات SSO |

**اصول هوش مصنوعی:** فقط دستیار تصمیم؛ بدون حذف خودکار کاربر؛ علت پیشنهاد به زبان ساده؛ بدون احتمال ساختگی/تضمین پذیرش؛ اعلام صریح «داده کافی نیست».

## ۳) جریان اصلی (معیار پذیرش)

```
ثبت درخواست (پیش‌نویس/انتشار، دامنه: همه/دانشکده/اساتید منتخب)
← مشاهده در استخر پژوهشی توسط استاد واجد شرایط
← اعلام آمادگی استاد (با شرایط)
← گفت‌وگوی مقدماتی (چت/فایل/جلسه)
← پذیرش پیشنهاد توسط دانشجو (سایر پیشنهادها «جایگزین‌شده» می‌شوند)
← امضای دوطرفه توافق‌نامه همکاری
← تشکیل دقیقاً یک پروژه (اتمی؛ در صورت نیاز، ابتدا تأیید مدیر پژوهش)
← فضای پروژه: وظایف، جلسات، فایل‌ها، پیشرفت، خاتمه
```

وضعیت‌های درخواست: `پیش‌نویس → منتشرشده → دریافت پیشنهاد → در حال مذاکره → توافق اولیه → در انتظار تأیید دانشگاه → متصل به پروژه` + `لغوشده/منقضی‌شده/بسته‌شده بدون توافق`
ضد تعارض: به‌روزرسانی شرطی اتمی + قید یکتایی `Project.request_id` — پذیرش هم‌زمان دو استاد هرگز پروژه تکراری نمی‌سازد.

## ۴) ورود یکپارچه با پرتال دانشجویار۳۶۰ (طبق سند ادغام رسمی)

پیکربندی اولیه **از قبل طبق سند ادغام ثبت شده است** و در استارت به‌صورت خودکار فعال می‌شود:

| مقدار | مقدار |
|---|---|
| Issuer | `http://188.212.96.235:8086` (بدون اسلش انتهایی — پورت ۸۰۸۶) |
| Client ID | `pazhoheshyar360` |
| نوع کلاینت | **public + PKCE (S256)** — بدون client_secret |
| scope | `openid profile email` |
| Redirect URI (وب) | `http://188.212.96.235:8000/sso/callback` ← با آدرس واقعی استقرار اصلاح کنید |
| Post-Logout Redirect | `http://188.212.96.235:8000/?loggedOut=1` |
| نقش پیش‌فرض | دانشجو (ایجاد خودکار حساب فعال است) |

تنظیمات علاوه بر جدول در **فایل آینه** `data/app_settings.json` نوشته می‌شود؛ با تعویض/بازسازی دیتابیس در استارت خودکار بازگردانده می‌شود (درس‌آموختهٔ سند، سناریوی پذیرش ۱۰).

### تنها قدم باقی‌مانده: ثبت client در پرتال
از مدیر SSO بخواهید کلید زیر را در `data/clients.json` پرتال اضافه و پرتال را یک‌بار ری‌استارت کند (اسنپت آماده در پنل مدیریت ← تنظیمات SSO هم هست):

```json
"pazhoheshyar360": {
  "name": "پژوهشیار۳۶۰",
  "confidential": false,
  "redirect_uris": ["http://188.212.96.235:8000/sso/callback"],
  "post_logout_redirect_uris": ["http://188.212.96.235:8000/?loggedOut=1"]
}
```

⚠️ Redirect URI باید **کاراکتربه‌کاراکتر** با آدرس واقعی سامانه یکی باشد؛ در صورت تغییر دامنه/پورت، هم فرم پنل و هم clients.json را هم‌زمان اصلاح کنید.

### پیاده‌سازی طبق سند (گام‌به‌گام)
- **گام ۱ — Discovery:** با کش کوتاه + مقایسهٔ سخت‌گیرانهٔ issuer (فقط یک اسلش انتهایی بخشیده می‌شود).
- **گام ۲ — شروع ورود:** `state`/`nonce`/`code_verifier` تصادفی، در کوکی **HttpOnly SameSite=Lax** با عمر ~۱۰ دقیقه؛ ریدایرکت 302 با `code_challenge_method=S256`.
- **گام ۳ — بازگشت:** تطابق state با کوکی؛ تبادل کد **در سمت سرور** با `code_verifier` و بدون secret؛ خطاها به پیام فارسی نگاشت می‌شوند: `idp_unreachable` (connection refused)، `expired` (کد ۱۲۰ثانیه‌ای تک‌مصرف)، `rate` (429)، `state`، `access_denied`.
- **گام ۴ — اعتبارسنجی id_token:** امضای RS256 از `jwks_uri` (کش ≤۱ ساعت + تازه‌گیری اجباری در نبود kid)، `exp`، تحمل اختلاف ساعت در `iat`، انطباق دقیق `iss` و `aud`، تطابق تک‌مصرف `nonce`، `sub` غیرخالی.
- **گام ۵ — پرووژنینگ:** ۱) اتصال با `sub` ذخیره‌شده ۲) اتصال حساب هم‌نام با `preferred_username` ۳) ساخت خودکار با نقش پیش‌فرض. نقش‌ها از `resource_access["pazhoheshyar360"].roles` — پسوند `.admin` یعنی مدیر سامانه.
- **گام ۶ — خروج:** ابطال نشست محلی + ریدایرکت به `end_session_endpoint` پرتال با `post_logout_redirect_uri` (دکمهٔ خروج سامانه خودکار انجام می‌دهد).
- **گام ۷ — پنل مدیریت:** فیلدهای کامل (برچسب دکمه، نوع کلاینت، post-logout و…) + «تست اتصال» که Discovery **و JWKS** را واکشی و تعداد کلیدها را گزارش می‌کند.
- لاگ رخدادهای SSO (شروع، موفقیت، خطاها) با کد خطا و IP در جریان رخدادها ثبت می‌شود؛ کاربر هرگز stack trace نمی‌بیند.

### تست سلامت و خطایابی سریع
```bash
GET http://188.212.96.235:8086/healthz     # {"status":"ok",...} یعنی پرتال روشن است
```
- پیام «connection refused» ⇒ سرویس پرتال اجرا نیست (`RUN-PORTAL.bat` روی سرور پرتال) یا پورت 8086 بسته است (`OPEN-FIREWALL.bat`).
- خطای «کلاینت ناشناس» ⇒ client_id در clients.json پرتال ثبت نشده یا ری‌استارت نشده.
- حساب‌های آزمون پرتال: `m.ahmadi / Student@360`، `s.hosseini / Staff@360`، `admin / Admin@360` (در محیط واقعی عوض شوند).

نقش‌ها همیشه در بک‌اند کنترل می‌شوند؛ مخفی‌کردن دکمه در فرانت هرگز کافی نیست.

## ۵) تست‌ها

```bash
cd backend && python -m pytest tests/ -q
```

شامل **۲۳ تست**، همگی سبز:

- **۹ تست پذیرش:** ورود و رمز نادرست، کنترل نقش‌ها، فهرست سرویس‌ها، **جریان کامل ثبت تا تشکیل دقیقاً یک پروژه**، مسیر تأیید دانشگاه، مسدودی اتصال متعارض، محرمانگی جزئیات، برچسب داده آزمایشی هوش مصنوعی، دسترسی جریان رخدادها.
- **۱۴ تست SSO پایان‌به‌پایان (سناریوهای پذیرش سند ادغام):** فعال‌سازی و تست اتصال (Discovery+JWKS) از پنل، ورود کامل با PKCE/S256 و ساخت خودکار حساب، ورود دوم بدون حساب تکراری، دستکاری state → رد خوانا، اتصال حساب موجود از پروفایل، تعارض هویت (409)، PKCE غلط، دستکاری nonce/iss/aud/exp در id_token → رد با پیام متناظر، نقش `.admin` از resource_access، اتصال حساب هم‌نام، خروج با end_session پرتال، غیرفعال‌سازی، پایداری فایل آینه، بازسازی تنظیمات اولیه.
