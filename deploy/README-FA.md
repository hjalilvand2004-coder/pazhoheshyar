# راهنمای استقرار پژوهشیار۳۶۰ روی سرور — پورت ۸۰۸۸

این راهنما دقیقاً برای استقرار تولیدی روی نشانی **http://188.212.96.235:8088** نوشته شده است و بخش ورود یکپارچه (SSO) را طبق «سند رسمی ادغام پرتال دانشجویار۳۶۰» (نسخه ۱.۰، متناظر با پرتال x.3.2) پوشش می‌دهد.

معماری استقرار:

```
مرورگر کاربر
   │
   ▼
http://188.212.96.235:8088   ← سامانه پژوهشیار۳۶۰ (این مخزن؛ FastAPI + SPA در یک سرویس)
   │  ورود یکپارچه: ریدایرکت به پرتال و بازگشت کد به /api/v1/auth/sso/callback
   ▼
http://188.212.96.235:8086   ← پرتال ورود یکپارچهٔ دانشجویار۳۶۰ (IdP؛ issuer)
```

هر دو سامانه روی یک سرور هستند و فقط هر کدام روی پورت خودشان. هیچ وابستگی دیگری (Node، دیتابیس خارجی، Nginx) لازم نیست؛ داده‌ها در SQLite و فایل‌های آپلودی داخل پوشهٔ `data/` و `uploads/` کنار مخزن نگه داشته می‌شوند.

---

## ۱) پیش‌نیازهای سرور

- لینوکس Ubuntu/Debian (یا هر لینوکسی با systemd و پایتون ۳.۱۰+)
- دسترسی sudo
- پورت **8088** آزاد و قابل دسترسی از اینترنت (پرتال روی 8086 از قبل فعال است)
- حدود ۵۰۰ مگابایت فضای خالی

## ۲) گام ۱ — استقرار سامانه (یک دستور)

```bash
git clone --depth 1 https://github.com/hjalilvand2004-coder/pazhoheshyar.git
cd pazhoheshyar
sudo bash deploy/deploy.sh
```

اسکریپت به‌صورت خودکار:

1. پیش‌نیازها (python3، venv، git، curl) را نصب می‌کند؛
2. مخزن را در `/opt/pazhoheshyar360` کلون/به‌روز می‌کند؛
3. کاربر سرویس `pazhoheshyar360` را می‌سازد؛
4. محیط مجازی `.venv` را می‌سازد و وابستگی‌ها را نصب می‌کند؛
5. پوشه‌های `data/` و `uploads/` را آماده و مجوزها را می‌دهد (کلید امضای نشست در `data/.secret` خودکار ساخته و پایدار می‌ماند)؛
6. سرویس systemd با نام `pazhoheshyar360` را نصب، فعال و اجرا می‌کند (پورت 8088، ری‌استارت خودکار در خطا)؛
7. تست سلامت می‌گیرد (`/api/v1/services` باید 200 بدهد) و پورت را روی فایروال باز می‌کند.

پس از پایان، این نشانی‌ها باید کار کنند:

| نشانی | انتظار |
|---|---|
| `http://188.212.96.235:8088` | صفحهٔ اصلی (SPA فارسی) |
| `http://188.212.96.235:8088/api/v1/services` | پاسخ 200 با فهرست سرویس‌ها |
| `http://188.212.96.235:8088/docs` | مستندات تعاملی API |

## ۳) گام ۲ — ثبت کلاینت SSO روی پرتال (الزامی، طبق سند رسمی)

> **در تست زندهٔ ۱۴۰۵/۰۸/۲۳ پرتال با خطای «کلاینت ناشناس — client_id=pazhoheshyar360 در سامانه ثبت نشده است» پاسخ داد؛ یعنی این گام هنوز انجام نشده و تا انجام آن، دکمهٔ ورود یکپارچه کار نمی‌کند.** باقی سامانه مستقل از این گام کاملاً فعال است.

پرتال، کلاینت‌ها را در فایل `data/clients.json` سمتِ خودش نگه می‌دارد (جدول ۲ سند: فیلدهای مجاز فقط `confidential`، `secret`، `redirect_uris`، `post_logout_redirect_uris`). بنابراین:

1. **روی همان سرور**، پوشهٔ نصب پرتال دانشجویار۳۶۰ (سرویس روی پورت 8086) را باز کنید و فایل `data/clients.json` آن را ویرایش کنید؛ بلوک زیر را (که در `deploy/portal-clients.json.snippet.json` همین مخزن هم آماده است) کنار کلاینت‌های دیگر اضافه کنید:

```json
"pazhoheshyar360": {
  "confidential": false,
  "redirect_uris": [
    "http://188.212.96.235:8088/api/v1/auth/sso/callback"
  ],
  "post_logout_redirect_uris": [
    "http://188.212.96.235:8088/"
  ]
}
```

2. سرویس پرتال را یک‌بار **بازراه‌اندازی** کنید (طبق سند: کلاینت‌ها در زمان راه‌اندازی خوانده می‌شوند).
3. طبق بند ۱۲ سند، سامانه را در **پنل مدیریت پرتال** نیز با همان `client_id` یعنی `pazhoheshyar360` در ستون کاتالوگ ثبت کنید تا کارت آن در صفحهٔ نخست ورود یکپارچه فعال شود.

نکته‌های مستقیم از سند:

- لیست‌سفید `redirect_uris` **پیشوندی** است؛ هر نشانی که با همین رشته شروع شود پذیرفته می‌شود و بقیه با خطا رد می‌شوند — پس مسیر callback را دست نزنید.
- کلاینت «عمومی» است (بدون `secret`) و جریان فقط با **PKCE/S256** انجام می‌شود؛ پیاده‌سازی همین سامانه از ابتدا همین‌طور ساخته شده است.
- اگر پرتال پشت پروکسی یا نام دامنه برود، فقط `PUBLIC_ORIGIN` پرتال عوض می‌شود و issuer تازه باید در پنل مدیریت همین سامانه به‌روز شود.

## ۴) گام ۳ — صحت‌سنجی ورود یکپارچه

به ترتیب چک کنید (مطابق چک‌لیست ۱۳ گانهٔ سند، موارد مربوط به سمت سامانه از قبل پیاده و تست شده‌اند):

1. `http://188.212.96.235:8088` را باز کنید و دکمهٔ «ورود با حساب پرتال دانشجویار۳۶۰» را بزنید؛
2. مرورگر باید به `188.212.96.235:8086/protocol/openid-connect/auth?...` با پارامترهای `response_type=code`، `client_id=pazhoheshyar360`، `redirect_uri`، `scope=openid profile email`، `state`، `nonce` و `code_challenge` (S256) برود؛
3. در پرتال با حساب پرتال وارد شوید؛ پرتال با کد کوتاه‌عمر به `http://188.212.96.235:8088/api/v1/auth/sso/callback?code=...&state=...` برمی‌گرداند؛
4. سامانه در پس‌زمینه: تطابق state (کوکی HttpOnly تک‌جریان) ← تبادل کد با `code_verifier` در بک‌اند ← اعتبارسنجی کامل id_token (RS256 با JWKS، `iss`، `aud`، `exp`، `nonce`) ← گرفتن userinfo ← پرووژنینگ حساب (اول `sub` ذخیره‌شده، بعد `preferred_username`، بعد ساخت خودکار) — همه مطابق بندهای ۵ تا ۷ سند؛
5. باید با نام فارسی خودتان داخل سامانه ببینید و حساب ساخته‌شده در پنل مدیریت قابل مشاهده باشد؛
6. از منوی کاربر خارج شوید: نشست محلی باطل و مرورگر به `end_session_endpoint` پرتال با `post_logout_redirect_uri=http://188.212.96.235:8088/?loggedOut=1` هدایت می‌شود (بند ۹ سند: خروج دووجهی).

چرا backchannel-logout لازم نیست؟ نشست این سامانه یک JWT مستقل با عمر ۱۲ ساعت است؛ با «خروج» صریح کاربر ابطال و به پرتال هم خبر داده می‌شود. پرچم `backchannel_logout_supported` پرتال برای سامانه‌های نشست‌محور است؛ در صورت نیاز آینده، مسیر قراردادی `/backchannel-logout` و ابطال بر اساس `sid` قابل افزودن است.

## ۵) تنظیمات SSO داخل همین سامانه (پنل مدیریت)

بخش «تنظیمات ورود یکپارچه» در پنل مدیریت سامانه، همین مقادیر را باید داشته باشد (به‌صورت پیش‌فرض تنظیم است؛ برای کنترل نهایی):

| فیلد | مقدار |
|---|---|
| فعال | ✔ |
| Issuer | `http://188.212.96.235:8086` |
| Client ID | `pazhoheshyar360` |
| نوع کلاینت | عمومی (public + PKCE) |
| Client Secret | (خالی — کلاینت عمومی) |
| Redirect URI | `http://188.212.96.235:8088/api/v1/auth/sso/callback` |
| URI پس از خروج | `http://188.212.96.235:8088/?loggedOut=1` |
| Scope | `openid profile email` |
| ساخت خودکار حساب | ✔ (نقش پیش‌فرض: دانشجو) |

دو نکته:

- در استقرار سرور، متغیرهای محیطی `SSO_REDIRECT_URI` و `SSO_POST_LOGOUT_REDIRECT_URI` (که در یونیت systemd ست شده‌اند) بر مقدار پنل **اولویت دارند** تا نشانی callback همیشه با `clients.json` پرتال یکی بماند. اگر خواستید از پنل مقدار دیگری بدهید، اول متغیر را از یونیت حذف و سرویس را ری‌استارت کنید.
- فایل آینهٔ `data/app_settings.json` به‌صورت خودکار پس از هر ذخیره در پنل به‌روز می‌شود و در تعویض دیتابیس، تنظیمات را برمی‌گرداند (سناریوی پذیرش سند).

## ۶) بهره‌برداری روزمره

| کار | دستور |

| وضعیت سرویس | `systemctl status pazhoheshyar360` |
| لاگ زنده | `journalctl -u pazhoheshyar360 -f` |
| ری‌استارت | `sudo systemctl restart pazhoheshyar360` |

متغیرهای محیطی مهم (در یونیت systemd قابل تغییر؛ پس از تغییر `daemon-reload` و restart):

| متغیر | پیش‌فرض | کاربرد |
|---|---|---|
| `PORT` | `8088` | پورت سرویس |
| `SSO_REDIRECT_URI` | `http://188.212.96.235:8088/api/v1/auth/sso/callback` | نشانی callback (اولویت بر پنل) |
| `SSO_POST_LOGOUT_REDIRECT_URI` | `http://188.212.96.235:8088/?loggedOut=1` | بازگشت پس از خروج پرتال |

| `SERVICE_TOKEN` | خالی | توکن سرویس‌به‌سرویس برای سایر «یارها» |

| `TOKEN_TTL_HOURS` | `12` | عمر نشست محلی |

## ۷) عیب‌یابی (بر اساس جدول ۵ سند + تجربهٔ استقرار)

| نشانه | علت | اقدام |
|---|---|---|
| «کلاینت ناشناس» در صفحهٔ پرتال | `pazhoheshyar360` در `data/clients.json` پرتال نیست | بخش ۳ همین راهنما |
| «ردِ redirect_uri» | نشانی callback با ثبت‌شده در پرتال یکی نیست | مسیر باید دقیقاً `http://188.212.96.235:8088/api/v1/auth/sso/callback` باشد (پیشوندی؛ بدون تغییری حرف‌به‌حرف) |
| «PKCE الزامی است» | درخواست authorize بدون code_challenge | در پیاده‌سازی فعلی این خطا رخ نمی‌دهد (PKCE همیشه فعال است) |
| «state نامعتبر» یا خطای state در callback | کوکی جریان منقضی (بیش از ۱۰ دقیقه بین شروع ورود و بازگشت) یا پشت پروکسی حذف کوکی | ورود را از نو شروع کنید؛ اگر پشت پروکسی است، هدر Host را دست‌نخورده عبور دهید |
| خطای اعتبارسنجی توکن بعد از تغییر آدرس پرتال | کش JWKS/issuer قدیمی | سرویس سامانه را ری‌استارت کنید (کش JWKS حداکثر ۱ ساعته خودش خالی می‌شود) |
| پاسخ 429 در ورود | سقف ۱۰ ورود در ۵ دقیقه برای هر IP (متغیر `RATE_LOGIN_LIMIT` پرتال) | چند دقیقه صبر کنید؛ برای تست بار با مدیر پرتال سقف را بالا ببرید |
| صفحه بالا نمی‌آید | پورت اشغال یا فایروال | `ss -ltnp | grep 8088` و `ufw allow 8088/tcp` |
| سرویس بالا نمی‌آید | خطای پایتون | `journalctl -u pazhoheshyar360 -n 100` |

## ۸) نکات امنیتی (چکیدهٔ بند ۱۰ سند — وضعیت فعلی این سامانه)

- **PKCE/S256 در همهٔ جریان‌ها** ✔ (پیاده‌سازی و تست‌شده)
- **state/nonce یک‌بارمصرف با عمر ~۱۰ دقیقه در کوکی HttpOnly SameSite=Lax** ✔
- **تبادل کد فقط در بک‌اند**؛ کد هرگز به فرانت نمی‌رسد ✔
- **اعتبارسنجی کامل id_token** (RS256 از JWKS با پشتیبانی چرخش کلید `kid`، iss، aud، exp، nonce) ✔
- **عدم نگهداری توکن پرتال در لاگ/URL/کوکی فرانت** ✔ (توکن محلی سامانه جداگانه و فقط سمت سرور صادر می‌شود)
- **رکورد کاربر با `sub` پایدار (UUID) لینک می‌شود** نه نام کاربری ✔
- **نقش‌ها فقط از `resource_access.pazhoheshyar360.roles`** خوانده می‌شوند و پسوند `.admin` مدیر سامانه می‌سازد ✔
- توصیهٔ سند: برای دسترسی از اینترنت، فعال‌سازی HTTPS روی پرتال/سامانه به‌شدت توصیه می‌شود چون کد ورود در URL کالبک ظاهر می‌شود؛ در حال حاضر مطابق استقرار جاری اکوسیستم (درسیار روی 8082 و برنامه‌یار روی 8083) HTTP ساده استفاده می‌شود.

## ۹) گزینهٔ جایگزین: داکر

اگر سرور داکر دارد، به‌جای systemd:

```bash
git clone --depth 1 https://github.com/hjalilvand2004-coder/pazhoheshyar.git
cd pazhoheshyar
sudo docker compose up -d --build
```

`docker-compose.yml` همین مخزن روی پورت 8088 و با همان متغیرهای SSO پیکربندی شده است؛ داده‌ها در والیوم‌های `pzh_data` و `pzh_uploads` می‌مانند.
